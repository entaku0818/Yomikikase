# VOICEVOX gateway の不正利用対策

2026-10-30。現在のiOS/AndroidのAPI形式を維持しながら、サーバーで負荷と外部呼出しを制限する。

## 今回追加した防御

値の正本は `internal/api/guard.go`。アプリを更新せずサーバーの変更で調整できる。

| 対象 | 制限（インスタンスごと） |
| --- | --- |
| 公開設定・キャラ一覧 | 合計5リクエスト/秒、瞬間20件 |
| その他のリクエスト | 認証処理の前に合計10リクエスト/秒、瞬間20件 |
| 検証済みApp Checkトークン・申告ユーザーID | それぞれ2リクエスト/秒、瞬間12件。両方を通る必要がある |
| 同時音声生成 | 2件。購入状態の照会・使用量予約・エンジン・エンコードを含む |
| 本文 | 64 KiB。JSONは1個のみ。チャンク転送や後続の巨大な空白も検証する |
| ヘッダー・認証トークン | ヘッダー16 KiB（Go HTTP実装の読込余裕分は別）、App Checkトークン8 KiB |
| タイムアウト | ヘッダー読込10秒、本文読込15秒、処理context100秒、書込115秒、idle60秒 |
| メモリ | 制限用キー最大4,096件、購入状態キャッシュ最大4,096人 |
| 外部応答 | RevenueCat 1 MiB、音声エンジン32 MiB |

短時間の制限は429 `rate_limited` と `Retry-After: 2` を返す。月上限の429 `quota_exceeded` と区別し、混雑を追加購入が必要な状態として扱わない。内部ヘルスチェックはレート制限しない。公開APIは別の枠なので、認証APIの連打で設定取得の枠まで消費しない。

- 本文・文字数・声の許可を購入情報の照会や利用量予約より先に検証する。
- 同じ利用者への同時購入照会をまとめる。キャッシュが満杯なら期限切れを掃除し、必要に応じて既存値を破棄して再取得する。
- 使用量文書が不正な型・負数・欠損なら0扱いせず停止する。返却はトランザクションで負数化を防ぎ、失敗時の返却処理にも5秒の期限を置く。
- エンジンのエラー本文をバッファに読み込まない。拒否したApp CheckのSDKエラー全文も毎回ログへ出さない。Cloud RunのHTTPステータスログは維持する。
- Cloud Run上の `LOCAL_DEV=1` を起動エラーにする。認証バイパスを本番で誤使用しない。
- 既存の署名・期限・対象Firebaseプロジェクト・許可アプリIDの検証、月の文字数トランザクション、声の許可リストを維持する。

## 残る境界と次のアプリ版で必要なこと

**App Checkは購入者本人の認証ではない。** `X-User-ID` は現行アプリが申告するRevenueCat IDで、本人との暗号学的な結び付きはない。検証済みトークンを持つ攻撃者がIDを変更して月枠を回避する問題や、他人の購入者IDを申告する問題は今回の速度制限だけでは解決しない。

次のアプリ版でFirebase Auth等の検証済みIDトークンを送り、サーバーが検証済みUIDから使用量キーとRevenueCat顧客を決める必要がある。端末申告の任意RevenueCat IDをそのまま結び付けてはいけない。既存購入の移行・復元とストア検証を設計し、旧アプリの移行期限と段階的な必須化を決める。匿名Authもアカウント再作成による無料枠回避を単独では防がない。有料Geminiや追加パックはこの本人確認・購入台帳が完成するまで有効化しない。

制限は各プロセス内のもの。別インスタンス、トークン更新、再起動にまたがる恒久的な端末制限ではない。トークンとIDの両方を変える攻撃や分散攻撃を完全には防げない。キー保存にはSHA-256を使うが、これは本人確認の代わりではない。IPやX-Forwarded-Forを信用した制限は行っていない。

Cloud Runの既存の最大インスタンス設定（サービス4、リビジョン3）を維持する。最大数や予算通知は請求額の絶対上限ではない。大量通信自体にも費用は発生し得る。必要になればロードバランサーとCloud Armor等による入口の制限を別途設計する。今回、追加の有料サービスは作成していない。

## 検証

- `go test -race ./...` / `go vet ./...` 成功。全6声・300字・無料/有料・旧形式の生成/使用量応答の互換性テストも成功。
- ローカルの偽エンジンで、入力不正時に購入照会・生成・文字消費がないこと、同時生成の上限、IDだけ/トークンだけの変更では連打制限を解除できないこと、メモリ上限・巨大な外部応答拒否を確認。
- Firestoreの公開ルールrelease一覧は空。`voicevox_usage` と `tts_policy` 内の存在しない確認用文書への認証なしREST読取りは両方403だった。書込みテスト・ユーザーデータ読取りは実施していない。将来ルールを追加する際もこれらのコレクションをアプリに公開しない。
- 本番への大量リクエスト試験は行わない。本番確認は少数の公開APIと認証不正・サイズ超過の拒否のみ。認証付き実音声生成の実機確認は未実施。

公式資料: [Firebase App Checkの役割と限界](https://firebase.google.com/docs/app-check)、[Cloud Runの最大インスタンス数](https://docs.cloud.google.com/run/docs/configuring/max-instances-limits)。
