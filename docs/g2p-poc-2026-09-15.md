## 0. 結論（先出し）

### 判定: **No — 「pyopenjtalk を iOS に組み込む」に 5〜10人日を払う価値は、現時点では無い。**

ただし **「日本語G2Pが音質のボトルネックである」という §1.4 の診断自体は正しい**。数字も英略語も実際に消えている。
Noなのは「G2Pが悪くないから」ではなく、**pyopenjtalk を入れても一番欲しかったもの（ピッチアクセント）が Kokoro-82M v1.0 には届かないから**であり、かつ**消える問題は pyopenjtalk 無しで直せるから**である。

根拠は3つ。詳細は §4。

1. **Kokoro-82M v1.0 の語彙(114記号)に、アクセントを表す記号が存在しない。** `_` `-` `^` はいずれも語彙外で、iOS側 `Tokenizer.swift` / Python側 `KModel.forward` の双方が**無言で捨てる**。つまり pyopenjtalk を移植してアクセントを算出しても、モデルに渡す経路が無い。
2. **実測で証明済み**: 「橋 / 端 / 箸」は misaki(pyopenjtalk) でも**音素列が完全に同一** (`haɕi`)。違いは `acc` 値 (2/0/1) だけで、それは語彙外のピッチ列にしか現れない。**pyopenjtalk を入れても 橋/端/箸 は同じ音になる。**
3. **数字・英略語の消失は、辞書の無いSwift側の前処理だけで直せる。** さらに、今回**別のもっと重大で、かつ1文字で直るバグ**を発見した（§3-E: `g` が全部消えている）。

### 「数字・英略語が消える問題は G2P 差し替えで直るのか」への回答

- **pyopenjtalk に差し替えれば直る（数字 8/8・英略語 9/9 が読まれる）。** これは事実。
- **しかし Kokoro公式の日本語G2P（misaki cutlet）に差し替えても直らない。** cutlet は数字 2/8 しか読まず、**英略語は 0/9**（現行アプリの 5/9 より悪い）。
- **つまり「Kokoro公式に寄せる」だけでは解決しない。** 解決に必要なのは読み下し（テキスト正規化）であって、これは pyopenjtalk 一式を持ち込まなくても Swift で書ける範囲。

## 1. §1.4 の仮説に対する訂正（重要）

§1.4 はこう書いている:

> Kokoro-82M の日本語音声は `misaki[ja]`（pyopenjtalk + full unidic、**アクセント記号あり**）の音素列で学習されている

**この前提は Kokoro-82M v1.0 については成り立たない。** 一次確認した事実:

| 確認項目 | 実測 |
|---|---|
| `kokoro` 0.9.4 の `KPipeline`、`lang_code='j'` の分岐 | `misaki.ja.JAG2P()` を**引数なし**で生成（`pipeline.py:114-117`）。`JAG2P.__init__` の既定は `version='cutlet'`（`misaki/ja.py:249`）→ **pyopenjtalk は使われない** |
| misaki の pyopenjtalk 経路の出力形式 | `return result + pitch`（`misaki/ja.py:356`）。音素列と**同じ長さのピッチ列を後ろに連結**して返す。インラインの `↓`/`↑` を出すコードは**コメントアウト済み**（`ja.py:310-320`） |
| Kokoro-82M v1.0 の語彙にピッチ記号はあるか | **無い**。`vocab['_']=None` `vocab['-']=None` `vocab['^']=None`（114記号中） |
| pyopenjtalk 経路が出す `ᶄ ᶃ ᶆ ᶉ`（拗音1文字表記） | **語彙外**。そのまま食わせると 東京 `toːᶄoː` → `toːoː` に化ける |
| misaki cutlet 経路の出力は語彙内に収まるか | **収まる**（英字を除き語彙外 0 文字、5本全て） |

→ **Kokoro-82M v1.0 の日本語の「正解」の入力は misaki cutlet 側の音素列であり、そこにアクセント情報は最初から無い。**
→ アクセントを扱いたいなら G2P ではなく**モデルを替える**話になる（§5）。

> 注: misaki の README が pyopenjtalk に言及しているのは事実だが、v1.0 のパイプラインと語彙の実測はいずれもそれを使っていない。Kokoro v1.1 系（`repo_id` が `/Kokoro-82M` 以外）は zh で別バージョンを使う分岐があるが、ja にそのような分岐は無い。

### 3-E. 🔴 副産物：`g` が1つ残らず消えている（1文字で直るバグ）

検証中に、仮説に無かった重大なバグを発見した。

- `JapaneseG2PProcessor.swift` の変換表は **ASCII の `g` (U+0067)** を出力する（`("が","ga")` など）。
- Kokoro の語彙にあるのは **IPA の `ɡ` (U+0261)** だけ。`vocab["g"] = nil`。
- `KokoroSwiftSources/TextProcessing/Tokenizer.swift:17-23` は `vocab[String($0)]` が nil の要素を `.filter { $0 != nil }` で**無言で捨てる**。

結果、**日本語の /g/ 音が1つ残らず消えて再生されている**。

| テキスト | 語彙外文字の合計 | うち `g` | その他 |
|---|---:|---:|---:|
| T1_kanji_proper | 3 | **3** | 0 |
| T2_digits | 5 | **5** | 0 |
| T3_acronym | 0 | 0 | 0 |
| T4_accent | 2 | **2** | 0 |
| T5_long | 46 | **46** | 0 |
| **合計** | **56** | **56 (100%)** | **0** |

現行アプリの語彙外文字は **100% がこの `g`**。具体例:

- 「神奈川」`kanagawa` → **`kanaawa`**（カナアワ）
- 「が」`ga` → **`a`**（助詞の「が」が全部「あ」になる）
- 「技術」`giʥɯʦɯ` → **`iʥɯʦɯ`**（イジュツ）

**修正は変換表の `g` を `ɡ` にするだけ**（`("が","ga")` → `("が","ɡa")` など14箇所）。工数は時間単位。
本PoCでは検証用に変換した WAV を **B_app_gfix** として別途生成してある（§4のパス一覧）。

> 本レポートの方針どおり、この修正は**適用していない**（iOSソースに触れないため）。別ワークスペースのクラウドTTS撤去作業と衝突しない形で、別途起票を推奨。

### 3-F. 副産物2：長音が展開されていない

| テキスト | A の `ː` 個数 | C の `ː` 個数 | A の `oɯ` 個数（＝本来 `oː` であるべき箇所） |
|---|---:|---:|---:|
| T1_kanji_proper | **0** | 7 | 5 |
| T5_long | **3** | 100 | 56 |

`CFStringTokenizer` が「東京」を `とうきょう` と返し、変換表がそれを `toɯkjoɯ` にそのまま写すため、**「トウキョウ」と1拍ずつ読まれる**（正しくは `toːkʲoː`）。長文では 56 箇所。
これも**変換表の後処理（`oɯ`→`oː`、`ei`→`eː`）で Swift 側だけで直せる**。

### 聴くときの推奨順と確認ポイント

1. **T2 の A → D**: 数字が読まれるかどうか。最も差が大きい。
2. **T3 の A → C → D**: C（Kokoro公式）が A より**悪い**ことの確認。
3. **T1 の A → B**: `g` 修正だけの効果（「カナアワ」→「カナガワ」）。**費用対効果が最良のはず**。
4. **T1 の B → C**: 長音（「トウキョウ」→「トーキョー」）の効果。
5. **T4 の A / C / D**: 橋・端・箸が**3つとも同じ音**であることの確認（＝pyopenjtalk では直らない証拠）。
6. **T5 の A / C / E / F**: 長文での総合的な自然さ。E（端末TTS）・F（クラウド）が現実的な比較対象。

> 聴取判断は人間（あなた）の担当。本レポートは音素列の客観数値までを担保する。

## 5. 判定と根拠

### **No（pyopenjtalk の iOS 組み込みに 5〜10人日を払うべきではない）**

| # | 根拠 | 数値 |
|---|---|---|
| 1 | **一番欲しかったアクセントが Kokoro-82M v1.0 に渡らない。** ピッチ記号 `_` `-` `^` が語彙114記号に存在せず、iOS/Python 双方が無言で捨てる | pyopenjtalk が出す 427 個のアクセント記号 → モデルに届く数 **0** |
| 2 | **アクセントで意味が変わる語は pyopenjtalk でも区別されない。** 橋/端/箸 の音素列は3経路すべて `haɕi` で同一 | 区別に使える語彙内の記号 **0 個** |
| 3 | **Kokoro公式の日本語経路(cutlet)自体がアクセント非対応。** つまりモデルはそもそもアクセント付き音素列で学習されていない | cutlet のアクセント記号 **0 個** |
| 4 | **「消える」問題は pyopenjtalk 無しで直せる。** 数字・英略語の読み下しは辞書不要のテキスト正規化。しかも現行の語彙外文字の **100% は単なる文字コードの取り違え** | `g`/`ɡ` 起因 **56/56 = 100%** |
| 5 | **コストが重い。** 辞書サイズを実測した。open_jtalk 辞書 = DL 22.6MB / **展開 102MB**、full UniDic = **777MB**。現状の同梱アセット（英語用）は17MB。加えて C/C++ の iOS 移植が要る | **最小構成（open_jtalk辞書のみ）でも展開102MB**。現状同梱17MBの**6倍**。`misaki` の読み精度を再現するなら UniDic 777MB も要る |

### 判定を覆しうる条件（正直に）

- **T4 の D を聴いて、橋/端/箸 が実際に区別されて聞こえた場合。** 音素列上は同一なので理論上あり得ないが、聴いて違えば私の読みが間違っている。
- **T2/T3 の D が A より「数字が読まれる」以上に、声質・抑揚の面でも明確に良い場合。** その場合は pyopenjtalk の**読み**（単語分割と読み推定）自体に価値があることになり、再評価が要る。ただしその場合でも、まず cutlet 相当（fugashi+UniDic）の移植で足りるかを先に問うべき。
- 上記2点は**あなたの聴取結果待ち**。数値からの私の予測は「どちらも No」。

### 代わりに推奨するもの（合計 3〜5人日、pyopenjtalk 不要）

| 優先 | 施策 | 工数 | 効果 |
|---|---|---|---|
| **1** | `JapaneseG2PProcessor` の変換表の `g` → `ɡ`（U+0261）。14箇所 | **数時間** | 日本語の /g/ 音が全滅している状態を解消。語彙外文字が 56→0 |
| **2** | 長音の後処理（`oɯ`→`oː`、`eɪ`/`ei`→`eː`）を `hiraganaToIPA` の後段に追加 | 0.5人日 | 長文で56箇所の「トウキョウ」読みを解消 |
| **3** | 数字の読み下し（アラビア数字→漢数字/かな、助数詞対応） | 1〜2人日 | 数字 0/8 → 8/8 相当 |
| **4** | 英字の読み下し（略語→カタカナ、`CFStringTokenizer` 頼みをやめる） | 1人日 | 英略語 5/9 → 9/9。`iOS`・`Google` が読まれるようになる |
| **5** | 未知文字を捨てる代わりにログに出す（回帰検知用） | 0.5人日 | 今回のような無言脱落の再発防止 |

施策1〜5はいずれも **`JapaneseG2PProcessor.swift` 1ファイル内で閉じ**、辞書の同梱もアプリサイズ増も無い。

### アクセントが本当に欲しい場合

G2P の問題ではなくモデルの問題なので、**Kokoro-82M v1.0 を使い続ける限り解決しない**。
選択肢は「アクセント入力を受け付ける日本語モデルへ乗り換える」だが、§3（2026-09-14 レポート）のとおり Style-Bert-VITS2 は AGPL、Piper は日本語非対応、VOICEVOX はクレジット表記必須で、**現時点で条件を満たす候補は無い**。
したがって当面は **A案（端末TTS の音声選択を効かせる）＋ 上記の Kokoro 前処理改善**で着地するのが妥当。
