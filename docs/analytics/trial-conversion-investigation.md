## 目的
無料トライアルから有料契約へ移らない理由を、既存データで検証する。各仮説を「支持する証拠あり／反する証拠あり／判定不能」に分類し、次に行う改善を1つ選ぶ。必要なデータを全て取得できるか自体も調査対象とする。初回デモの参加率改善とは別の調査。価格・導線・計測の実装は分析後に子Issueへ切り出す。

## 基準値と前提
2026-11-07の既存RevenueCat調査では、9月開始3件・10月開始7件とも有料転換0、未転換終了。11/1〜6開始4件は保留中。RCのproduction/store/product条件は再現・確認が必要。
10月GA4 iOSの課金画面は99人141回、購入成功は6人7回。購入成功は無料試用開始も含むので有料請求とは扱わない。購入シートキャンセルと、試用開始後の更新停止も別物。
ローカル作業ツリーには未公開変更がある。公開バージョンとイベント実装の対応を必ず確認する。

## 仮説と、支持・反証に必要なデータ
| 仮説 | 必要データ | 支持するパターン／反するパターン | 限界 |
|---|---|---|---|
| H1: 試用を始めたが具体的な用途が定着しない | 試用開始前の導線、実コンテンツ利用、開始後の再訪・更新停止時刻 | 計測が有効なのに初日以外の利用がない／複数日の実利用があれば弱まる | 開始直後の更新停止だけでは判定しない。課金忘れ防止で停止して使い続ける場合がある |
| H2a: 有料機能を発見・体験できていない | 音声エンジン選択、モデル準備、合成・再生開始・成功、利用上限、体験までの時間 | 有料音声を選んでも準備や再生に到達しない／繰り返し成功していれば弱まる | トグルONや再生リクエストは音が出た証明ではない |
| H2b: 不具合や待ち時間で価値を体験できない | エンジン別エラー、準備時間、最初の音声までの時間、クラッシュ、停止理由 | 失敗・長い待ちの直後に利用停止／正常再生の反復なら弱まる | 過去イベントがなければ取得不能。クラッシュ全体集計を試用者の障害と扱わない |
| H3: 無料で足りる／一度きりの用途 | 試用中・終了後の利用日数、量、無料上限との比較、有料専用機能の利用 | 終了後も無料範囲で継続／上限超過用途や有料機能の反復なら単純な無料充足説は弱まる | 利用停止だけでは一度きり・不満・他製品への移行を区別できない |
| H4a: 価格・契約期間・期待が合わない | 契約時の商品・価格・通貨・試用条件、プラン、更新停止時刻、任意の理由回答 | 価値体験・継続利用はあるが有料移行せず、価格等の回答が一致／他理由なら弱まる | 月額と年額の相関や解約時刻だけで価格を原因と断定しない。未回答者の理由は推測しない |
| H4b: 支払う意思はあるが決済失敗 | BILLING_ISSUE、キャンセル/期限切れ理由、猶予期限、復旧・初回請求 | 試用終了時に請求失敗し未回復／自発的更新停止のみなら弱まる | 決済失敗の存在は支払う意思そのものの証明ではない。観測終了時点の回復待ちを分離 |

## 調査手順
### 1. RCで「誰の、いつの試用か」を確定
- [ ] Production/App Storeを主集団としAndroid・Sandbox・復元・買い切り・通常更新を分離。9〜10月開始10件と11月保留4件を同条件で再集計。差が出たら元集計との条件差を記録。
- [ ] 顧客API・購読API・顧客履歴・既存export/webhook保存先の取得可否、権限、保存期間を一覧化。API不可を「データが存在しない」と扱わずダッシュボード/exportも確認。
- [ ] 試用単位で開始、商品、ストア、環境、予定終了、更新停止と再開、失効、請求失敗、猶予、最初の有料請求、返金を時系列化。イベント時刻と通知受信時刻を区別。
- [ ] aliases/transfer/再インストールを確認し、顧客数・契約数・試用数を混ぜない。生IDはアクセス制限した分析内だけで保持し、Issueには集計と仮番号のみ。

### 2. GA4/BigQueryと契約を結合できるか判定
- [ ] RCの既存subscriber attributes（$firebaseAppInstanceId等）、Firebase/GA連携設定、既存サーバー記録から、過去の決定的な対応関係を探す。
- [ ] 結合成功件数/対象件数、多対一・一対多、欠損、aliases処理を記録。時刻・国・端末・プランが似ているだけの結合は禁止。
- [ ] 結合できればRC試用者コホートで分析。結合できなければ、RC課金ライフサイクルとGA4購入成功者の行動を別表で出す。trial_eligible=trueでも試用開始確定と扱わない。
- [ ] GA4側はuser_pseudo_id単位の順序付き行動を再構成できる。購入成功の複数回発火を同一試用として自動結合せず、契約者とは別の「購入成功イベントを持つインストール」の参考分析とする。

### 3. 実コンテンツ利用と価値体験を調べる
- [ ] 開始前7日、開始後0〜24h・24〜48h・72〜96h・168〜192h、試用中全体、失効後7日を取得。D1/D3/D7の経過時間定義を固定し、観測期間不足を未利用にしない。各プランの実際の試用終了時刻でも区切る。
- [ ] 再訪日数、アクティブ利用、初回実コンテンツ利用までの時間、複数日再生、利用元（PDF/テキスト/EPUB等）、標準/Kokoro/VOICEVOX、完了・停止・失敗を、実際に記録がある範囲で集計。
- [ ] イベント×アプリバージョン×期間×再生経路の計測対応表を作成。旧speech_completedの欠測、新content_playbackイベントの未導入をゼロ利用に置き換えない。完了は文書全体を聴いた証明ではなく、途中停止も失敗とは限らない。
- [ ] VOICEVOX本番の月次利用量や既存ログがRCと結合できるか確認。月次量を試用7日間の利用量として割り当てない。本文・タイトル・メール等は分析に収集しない。
- [ ] 同一アプリ内で転換者がいれば同等観測期間で比較。9〜10月は転換者0のため、非転換者内の利用パターンを記述する。他アプリを対照群にして因果推論しない。

### 4. 取得できない項目だけ、将来の計測候補にする
- [ ] データ項目ごとに「過去を取得済み／保存あり未検証／権限不足／過去は未計測／回答が必要」を付ける。
- [ ] 必要なら契約・行動の安全なID連携、RCライフサイクル連携、エンジン/再生成功/エラー/待ち時間/停止理由の最小イベントを設計。既存イベントと重複させず、再送・復元の重複排除を定義。
- [ ] 今から設定する連携やイベントで過去が復元されるとは仮定しない。新計測は公開版・計測開始日を明記。
- [ ] 価格・用途・音声品質の主観的理由は既存の任意フィードバックに証拠があるか確認し、足りなければ任意の理由質問を別案にする。回答収集やユーザーへの連絡はこの調査では実施しない。

## 成果物・完了条件
- [ ] 各必要項目の取得元・実測した可否・対象期間・欠測・代替手段がある「取得可能性一覧」。
- [ ] RCの成熟済み試用と保留中を分けた基準表、および再現可能なクエリ/取得条件。UTC/JSTを明記し日別ユニークを合算しない。
- [ ] 結合率付きの匿名化時系列。結合不能ならRC表とGA4参考表を分け、試用者の行動は不明と明示。
- [ ] H1〜H4bごとに支持/反証/判定不能、根拠件数、欠測、代替説明を記載。全仮説の判定が可能とは約束しない。
- [ ] 少数例では率だけでなく分子/分母を示す。観測結果と因果関係を区別し、次に試す改善1件または不可欠な計測1件を選ぶ。
- [ ] 次施策には公開日、対象、評価期間、成熟済み試用の有料転換率、利用成功率等の補助指標とガードレールを設定。
